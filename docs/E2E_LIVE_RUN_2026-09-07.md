## Findings

### F1 — Pause status-update tx reports "confirmed" but never actually spends the escrow coin on-chain

**Severity**: High (functional correctness; same failure class as fragility #53, a different code path).

**Where**: `dapp/app.js` `buildAndPostStatusUpdateTx` / `finalizeStatusUpdate` (the V3/V4 on-chain campaign-status-update tx builder used by Pause/Resume/Finish in `mycampaigns.js`).

**Repro (live, 6-node harness, campaign `1a07bf74d93-1-7755c3ab1f1d0e51`, V4 escrow)**:
1. Node 1 (creator) clicks **Pause** on an active campaign whose escrow coin (`0x2093B36F...`, amount 999, `ESCROW_ADDRESS_V4`) is currently unspent, `STATE(7)=active`.
2. Console logs the full success sequence: `[STATUS-TX] confirmed. campaign: ... status: paused new coinId: 0xE82C0B60...` and `[STATUS-TX] confirmed on-chain for ... new coinid: 0xE82C0B60...`.
3. Local DB updates immediately: `CAMPAIGNS.STATUS='paused'`, `ESCROW_COINID='0xE82C0B60...'`. UI shows "Paused" with Resume/Finish buttons. Zero console errors anywhere in the sequence.
4. **Ground truth via `MDS.cmd("coins coinid:...")` run directly in the page (bypassing all app/DB caching), on Node 1 itself**, ~2 minutes later:
   - `coins coinid:0xE82C0B60...` (the claimed new coin) → `response: []` — **does not exist on-chain, anywhere, not even on the creator's own node.**
   - `coins coinid:0x2093B36F...` (the coin that was supposedly spent) → still present, `"spent":false`, `STATE(7)` still `0x616374697665` (`"active"`) — **the input coin was never actually spent.**
5. Node 3 (viewer), independently, after 3 full page reloads and 45+ seconds / 15+ NEWBLOCKs, still shows the campaign as `Active` in its own local DB (`SELECT STATUS FROM CAMPAIGNS` → `active`), which is actually the *correct* state given #4 — the propagation "gap" (F1 was initially suspected as a viewer-side reconciliation bug; investigation redirected to the real root cause: there is nothing to propagate, the pause never happened on-chain).

**Root cause (found)**: `core/campaigns.js`'s `buildStatusUpdateStatePorts()` sets ports 1, 3, 4, 5, 6, 7, 10, 11 — but never port 16 (`foundationfeeflag`). `ESCROW_SCRIPT_V4` reads `STATE(16)` unconditionally at top level (`LET foundationfeeflag=STATE(16)`, no guard). Same bug class as fragility #49 (fixed 2026-06-09 in the split/channel-open tx builders) — this status-update tx builder is a *third* code path that needed the same "every top-level `STATE(n)` port must be set" treatment and was missed (added later, for the V3/V4 on-chain status flow).

**Impact**: any creator clicking Pause/Resume/Finish on this code path gets a false "success" — the campaign silently keeps running exactly as before (still charging budget, still active) while the UI tells them otherwise. Correctness/trust issue, not a security one.

**Fix (applied and verified live, same session)**: added `{ port: 16, value: '0' }` to `buildStatusUpdateStatePorts`'s returned array. Redeployed; confirmed the corrupted local DB state (from the pre-fix false-success write) **self-healed** via the pre-existing, unrelated `processEscrowCoin` discovery/reconciliation logic — no manual DB repair needed. Re-ran Pause → Resume → Finish, verifying each with `MDS.cmd("coins coinid:...")` ground truth: all three now genuinely confirm on-chain (`STATE(7)` = paused/active/finished, `STATE(16)="0"`). Node 3 propagation re-confirmed clean post-fix too. Recorded as fragility #55 in `docs/KNOWN_ISSUES.md` §3; full narrative in `docs/HISTORY.md §17`, session 2026-09-07.

### F2 — Manual campaign Finish never auto-settles a remote viewer's open channel (only self-computed block-expiry does)

> **✅ Fixed 2026-09-07** — see `docs/HISTORY.md §17`, session 2026-09-07 (OPEN-3). The repro and analysis below are preserved verbatim as the original finding; only this note and the "Not fixed this session" paragraph at the end were added afterwards. Two corrections the fix session established: (a) the root cause was **three** defects, not one — beyond the missing send, `applyStatusChange` also marked the *receiving* node's own channel `'settling'` before signalling the FE, so the FE's `WHERE STATUS='open'` query could never have matched even if the message had arrived; and (b) the "Why this probably isn't intentional" reasoning below — that the on-chain path is already cryptographically authenticated — is **wrong as stated**, and acting on it would have been dangerous: see OPEN-4 in `docs/KNOWN_ISSUES.md` §1b. The publisher half (point 6) was resolved as a documentation fix, not a code change.

**Severity**: Medium-High (functional correctness, not security — money isn't lost, it's just stuck until someone remembers to click Settle manually).

**Where**: `dapp/views/mycampaigns.js` `_applyStatusChange` (creator FE), `public/service-workers/handlers/campaign.handler.js` `processEscrowCoin`'s on-chain STATUS-sync block, `dapp/app.js` `_autoSettleOpenChannels`.

**Repro (live, real 6-node harness, campaign `1a07c5b8079-8-d906ea901e5778a0`)**:
1. Node 1 (creator) publishes a fresh 100-MINIMA campaign.
2. Node 3 (viewer) watches the ad → real open viewer channel, `CUMULATIVE_EARNED=0.02`, deliberately **not** settled manually.
3. Node 2 (publisher, real Frame `1a07c5a6e30-1-667be4065047c49d`) gets a real publisher channel via a genuine `MA_TRACK_VIEW` (frameId+publisherKey+publisherMx, driven from Node 3's own SW to simulate a real third-party-site visit) → `CUMULATIVE_EARNED=0.002`, also unsettled.
4. Node 1 clicks **Finish**. Console confirms `CAMPAIGN_AUTOSETTLE_REQUEST received campaign: ... channels: 2` (SW correctly found both). Both rows flip to `CHANNEL_STATE.STATUS='settling'` **on Node 1**.
5. **Node 1 (creator) can never actually post either settlement tx** — by design (`_handleAutoSettleRequest`: "L1 txs require viewer co-sign, skipping post"). Both channels are permanently stuck at `'settling'` on the creator's own row unless the counterparty settles independently.
6. **Publisher (Node 2)**: per design (Fix #12, `_autoSettleOpenChannels` explicitly `if (role === 'publisher') return;`), never auto-settles via this path — confirmed correct, this is **7f**, working as documented.
7. **Viewer (Node 3)**: this is the one that's *supposed* to self-settle (`_autoSettleOpenChannels`, gated on `CAMPAIGN_UPDATED.settling===true`). Waited 35+ seconds, reloaded, re-checked: `CHANNEL_STATE.STATUS` stayed **`'open'`** the entire time — never auto-settled. Node 3's own `CAMPAIGNS.STATUS` **did** correctly flip to `finished` (on-chain reconciliation propagated fine) — only the `settling:true` flag, and therefore the auto-settle trigger, never arrived.

**Root cause**: `grep`ing the whole repo for anywhere a `CAMPAIGN_FINISH`/`CAMPAIGN_PAUSE` Maxima message is actually *sent* (as opposed to just handled on receipt) returns nothing — the fast-path broadcast MinimaAds.md §6.7/§8.5 describes ("SW detects campaign STATUS='finished' with settling:true via CAMPAIGN_FINISH Maxima...") does not exist in the current code; only the RECEIVE handler (`handleCampaignFinish`, kept for the AUD-3-era spoofing defenses) is implemented. The creator's `_applyStatusChange` only does a same-node `MA_LOCAL_STATUS` self-broadcast (reaches the creator's own SW instantly, which is why Node 1's own `autoSettleChannelsForCampaign` fired) plus the real on-chain status-update tx (this session's F1 territory). Remote nodes only ever learn the new status via `processEscrowCoin`'s on-chain STATUS-sync block, which calls the bare `setCampaignStatus` (DB-only) — **not** `applyStatusChange` — so `settling:true` is never set for a remote node, and `_autoSettleOpenChannels`'s gate never trips.

**Why this probably isn't intentional**: unlike a spoofable Maxima payload (the exact vector AUD-3/AUD-5 closed by requiring `settling:true` only from a strongly-verified sender), the on-chain reconciliation path is **already cryptographically authenticated** — `processEscrowCoin` only accepts a `STATE(7)` change carried by a coin that required `SIGNEDBY(creatorkey)` to produce. Gating viewer auto-settle on `settling:true` made sense as a defense against spoofed Maxima; it seems to have also accidentally cut off the one remaining channel (on-chain discovery) that *is* trustworthy, leaving no live path for a remote viewer to auto-settle at all outside the narrow case where that same viewer's own node independently computes block-based expiry (7e) and runs its own local `applyStatusChange`.

**Impact**: in practice, "auto-settle when a campaign finishes" only reliably works today for the creator's own co-located channels (never — creator can't self-post) and for viewers whose own node happens to independently reach the same block-expiry conclusion (7e's mechanism). A manually-Paused/Finished campaign's remote viewers keep an open, unsettled channel indefinitely until they happen to open `#earnings` and click Settle themselves.

**Fixed in a later session the same day** — see `docs/HISTORY.md §17`, session 2026-09-07 (OPEN-3), and the note at the top of this finding. Original triage note, kept for the record: **Not fixed this session** — this touches the same settlement-trust boundary as AUD-3/AUD-5/Fix #12 (a real security-sensitive area with prior audit history), so it needs the maintainer's explicit sign-off and probably HIGH-complexity plan-mode treatment (multi-layer: SW discovery logic + FE gating + re-examining whether authenticating off the on-chain read is actually as safe as it looks) rather than a quick patch. Recorded as **OPEN-3** in `docs/KNOWN_ISSUES.md §1b` — maintainer confirmed continuing the fix design in a fresh session (Opus + plan mode). That session should start from `KNOWN_ISSUES.md` OPEN-3 and this finding, not re-derive the repro.

**Also worth re-checking, not yet isolated**: in the F2 repro, the publisher's own node (Node 2) never received *any* Maxima message about its channel — `CHANNEL_STATE` stayed completely empty there for 5+ minutes, even though the creator's side showed a real, correctly-attributed publisher channel (`CUMULATIVE_EARNED=0.002`, `VIEWER_KEY`=Node 2's own pubkey). Could be a genuine delivery bug in the `PUBLISHER_REWARD_NOTIFY`/`DEFERRED_PUB_REWARDS` path, or could just be that Finish was clicked before the deferred-retry-on-NEWBLOCK had a chance to run — the test window was short (~30s from view to Finish). Not confirmed either way; would need a repeat with a longer gap before Finish, and reading Node 1's raw log (not just its FE console, which doesn't carry `MDS.log()` SW output) for `[CHANNEL] _notifyPublisherByKey` / `[CHANNEL] _deferPublisherReward` lines.

**Still open**: the auto-settle-on-Finish payload (`autoSettleChannelsForCampaign`/`CAMPAIGN_AUTOSETTLE_REQUEST`) was not exercised — see 7c note.
